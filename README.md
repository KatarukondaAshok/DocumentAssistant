# Intelligent Document Assistant

A full-stack RAG (Retrieval-Augmented Generation) application that lets a user
sign up, upload PDF/DOCX/TXT documents, and chat with them — answers come
**only** from the uploaded content, not from the model's general knowledge.

Built for: AI/ML Internship Assignment
Stack: **FastAPI + Streamlit + LangChain + ChromaDB + JWT + SQLite**

---

## 1. Architecture Overview

```
                    ┌─────────────────────┐
                    │   Streamlit UI       │
                    │  Login / Upload /    │
                    │  Chat / History      │
                    └──────────┬───────────┘
                               │ REST (HTTP + JWT)
                    ┌──────────▼───────────┐
                    │     FastAPI Backend   │
                    │ ┌───────────────────┐ │
                    │ │ auth.py  (JWT,     │ │
                    │ │ bcrypt hashing)    │ │
                    │ ├───────────────────┤ │
                    │ │ routes.py (APIs)   │ │
                    │ ├───────────────────┤ │
                    │ │ rag.py (LangChain) │ │
                    │ └─────────┬─────────┘ │
                    └───────────┼───────────┘
                    ┌───────────▼──────────┐   ┌────────────────────┐
                    │   SQLite (SQLAlchemy) │   │      ChromaDB       │
                    │  users / documents /  │   │  (vector embeddings │
                    │  chat_history         │   │   per document)     │
                    └───────────────────────┘   └────────────────────┘
```

### RAG Pipeline Flow
```
Upload File → Load (PyPDF/Docx2txt/Text) → Chunk (RecursiveCharacterTextSplitter)
   → Embed (SentenceTransformers: all-MiniLM-L6-v2) → Store (ChromaDB collection)

User Question → Embed Question → Semantic Search (top-k chunks)
   → Build strict Context Prompt → LLM (OpenAI/Ollama) → Answer + Sources
```

Each document gets its own ChromaDB collection named `user{id}_doc{id}`,
which keeps every user's data isolated and makes per-document deletion clean.

## 2. Database Schema

| Table          | Columns                                                                 |
|----------------|--------------------------------------------------------------------------|
| `users`        | id, username, email, hashed_password, created_at                        |
| `documents`    | id, user_id (FK), filename, filepath, file_hash, collection_name, uploaded_at |
| `chat_history` | id, user_id (FK), document_id (FK, nullable), question, answer, timestamp |

- `file_hash` (SHA-256) is used for **duplicate detection** on upload.
- `document_id` is nullable in `chat_history` because a question can be
  asked across *all* of a user's documents at once.

## 3. REST API Reference

| Method | Endpoint          | Auth | Description                                  |
|--------|-------------------|------|-----------------------------------------------|
| POST   | `/signup`         | No   | Create account, returns JWT                   |
| POST   | `/login`          | No   | Authenticate, returns JWT                      |
| POST   | `/upload`         | Yes  | Upload + ingest a PDF/DOCX/TXT file            |
| POST   | `/chat`           | Yes  | Ask a question or request a summary            |
| GET    | `/history`        | Yes  | List the user's past Q&A                       |
| DELETE | `/history/{id}`   | Yes  | Delete one history entry                        |
| GET    | `/documents`      | Yes  | List uploaded documents (used by the frontend) |
| DELETE | `/documents/{id}` | Yes  | Delete a document + its vectors                |

Interactive Swagger docs are auto-generated by FastAPI at:
**http://localhost:8000/docs**

## 4. Setup & Installation

### Prerequisites
- Python 3.10+
- An OpenAI API key (or Ollama installed locally for a free option)

### Step 1 — Clone / unzip the project
```bash
cd DocumentAssistant
```

### Step 2 — Backend setup
```bash
cd backend
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt

cp ../.env.example .env       # then edit .env and add your OPENAI_API_KEY
```

### Step 3 — Run the backend
```bash
uvicorn app:app --reload --port 8000
```
Visit http://localhost:8000/docs to confirm it's running.

### Step 4 — Frontend setup (new terminal)
```bash
cd frontend
python -m venv venv
source venv/bin/activate
pip install -r requirements.txt
streamlit run streamlit_app.py
```
Visit http://localhost:8501

### Using a free local LLM instead of OpenAI
1. Install [Ollama](https://ollama.com) and run `ollama pull llama3`
2. In `.env`, set `LLM_PROVIDER=ollama`
3. Restart the backend — no API key needed.

## 7. Interview Preparation — Q&A

**Q1. What is RAG?**
Retrieval-Augmented Generation combines a retrieval step (semantic search
over your own data) with a generation step (an LLM). Instead of relying on
the model's frozen training data, you fetch relevant, up-to-date chunks at
query time and feed them into the prompt as context. This grounds the
answer in real, verifiable source material and works for private/internal
documents the model has never seen.

**Q2. Why use embeddings?**
Embeddings convert text into dense numeric vectors that capture semantic
meaning. Two sentences with similar meaning end up close together in vector
space even if they share no exact words. This is what makes *semantic*
search possible — matching by meaning, not keyword overlap.

**Q3. Difference between ChromaDB and FAISS?**
- **ChromaDB**: a full vector *database* — it manages persistence, metadata
  filtering, and collections out of the box, with a simple Python API. Great
  for getting a RAG app running fast.
- **FAISS**: a lower-level vector *search library* from Meta. Extremely fast
  and memory-efficient for large-scale similarity search, but you build the
  persistence/metadata layer yourself.
In short: Chroma = batteries-included database; FAISS = a high-performance
search algorithm you wire up yourself.

**Q4. What is semantic search?**
Search based on the *meaning* of a query rather than exact keyword matches.
The query is embedded into the same vector space as the stored chunks, and
the closest vectors (by cosine similarity, typically) are returned as the
most relevant results.

**Q5. Why chunk documents?**
1. LLMs have a limited context window — you can't feed a 200-page PDF in
   one shot.
2. Smaller, focused chunks produce more precise embeddings and more
   relevant retrieval than one embedding for an entire document.
3. Overlap between chunks (e.g. 150 characters) prevents losing context
   that straddles a chunk boundary.

**Q6. How does JWT work?**
JWT (JSON Web Token) is a self-contained, signed token with three parts:
header, payload, and signature. On login, the server signs a payload
(e.g. `{"sub": "username", "exp": ...}`) with a secret key and returns it.
On every subsequent request, the client sends the token in the
`Authorization: Bearer <token>` header; the server verifies the signature
(no database lookup needed) to confirm the request is authentic and not
expired. This makes authentication **stateless** — it scales horizontally
without shared session storage.

**Q7. Why is password hashing needed?**
Storing plain-text passwords means a single database breach exposes every
user's real password. Hashing (bcrypt, in this project) is a one-way
function: it's computationally cheap to hash a password but infeasible to
reverse. bcrypt also **salts** each hash automatically, so two identical
passwords never produce the same hash, defeating rainbow-table attacks. It
is also deliberately slow, which throttles brute-force attempts.

**Q8. Difference between SQL and a Vector Database?**
- **SQL (SQLite/Postgres)**: stores structured, relational data; you query
  with exact matches, joins, and filters (e.g. "get all chats for user_id=5").
- **Vector DB (ChromaDB)**: stores high-dimensional embeddings and answers
  "what's most *similar* to this?" queries via nearest-neighbor search.
They're complementary, not competitors: this project uses SQL for
users/history (structured, exact) and Chroma for document content
(unstructured, similarity-based).

**Q9. How are hallucinations reduced in RAG?**
1. The prompt explicitly restricts the model to only use the provided
   CONTEXT, with an instruction to say "I don't know" if the answer isn't
   there.
2. Retrieval only returns the top-k most relevant chunks, keeping context
   focused and reducing the temptation for the model to fill gaps.
3. `temperature=0` makes generation more deterministic/factual rather than
   creative.
4. Returning source snippets alongside the answer lets the user verify the
   claim against the original text.

**Q10. Describe the LangChain workflow used here.**
Loaders (`PyPDFLoader` / `Docx2txtLoader` / `TextLoader`) read the raw file
→ `RecursiveCharacterTextSplitter` breaks it into overlapping chunks →
`HuggingFaceEmbeddings` (Sentence-Transformers) turns each chunk into a
vector → `Chroma.from_documents` stores those vectors as a collection. At
query time, `similarity_search_with_relevance_scores` retrieves the closest
chunks, which are inserted into a strict prompt template and sent to the
chat LLM (`ChatOpenAI` or `ChatOllama`) to produce the final answer.
